# History, exact numbers and model data policy

Implemented on 14 November 2026 as the first increment of [HARDENING_PLAN.md](HARDENING_PLAN.md). This covers the core of issues 1, 2 and 8. It does not complete the eight-issue plan.

## Saved query history

The application distinguishes the one-hour completed-job memory cache from durable history. New records expire **24 hours after submission**, configured through `HISTORY_RETENTION_HOURS` in `.env` (positive, at most 366 days). Changing this setting affects new registrations; existing deadlines remain fixed. Reads, feedback, confirmation and writes check the durable deadline, including across restart. A background task runs at startup and every minute, deleting up to 200 expired query snapshots and their feedback per pass. Expired records are inaccessible even when physical cleanup is delayed.

`HISTORY_STORE_RESULT_ROWS=false` is the default. Durable snapshots omit raw result rows; question text, SQL, parameters, answers, reasons, table decisions and feedback can still be sensitive. Live results remain in memory until cache eviction or expiry. The existing encryption flag separately controls encryption of application records. Changing a storage setting does not rewrite existing snapshots.

The UI's **Hide list** removes browser references only. **Delete saved history** asks for confirmation and deletes the current account's live saved queries and related feedback from the application's records database. It is protected by authentication and CSRF checks. Administrators clearing their history do not implicitly clear other users' records. The API also supports owner-scoped individual deletion. Deletion leaves a small lifecycle tombstone until seven days after the original expiry. Late workers cannot recreate deleted data, including after tombstone cleanup, because only explicitly registered IDs can be saved.

Deletion/expiry cancels waiting confirmations and prevents subsequent workflow stages from proceeding, but cannot undo a provider request or SQL already in progress. Browser displays expire locally; data already copied outside the application cannot be recalled. Backups, restored databases, filesystem remnants and device snapshots require separate operator handling. A restored backup can reintroduce records: deletion-ledger replay and backup retention automation are not implemented.

### Existing records

Records created before lifecycle metadata existed are marked `legacy_pending` and hidden from every HTTP user, including administrators. Startup does not silently adopt or purge them. Inventory reports counts without printing questions or results. From this directory:

```powershell
.\run.ps1 --history-maintenance inventory
.\run.ps1 --history-maintenance adopt-legacy
.\run.ps1 --history-maintenance adopt-legacy --apply
.\run.ps1 --history-maintenance purge-expired --apply
```

Adoption without `--apply` is a dry run. Adoption uses each record's original timezone-aware creation timestamp plus the configured retention; it does not grant a fresh lifetime. Future, malformed or unreadable timestamps remain quarantined. An operator who has reviewed the consequences can instead use `--history-maintenance purge-legacy --apply`; this deletes quarantined payloads and their feedback. No adoption or legacy purge was executed as part of implementation. `GET /api/admin/history-retention` provides administrator-only counts and active settings.

This lifecycle currently covers application query snapshots and associated feedback. Evaluation reports/checkpoints, security audit metadata, external logs and backups still need their own retention policies and implementation. The lifecycle database and CLI are trusted operator resources.

## Exact numeric values

Warehouse-native `Decimal` values remain decimals instead of becoming binary floats. At JSON boundaries they are represented explicitly:

```json
{"$qd_type":"decimal","value":"12345678901234567890.0100"}
```

Integers beyond JavaScript's safe range use `{"$qd_type":"integer","value":"9007199254740993"}`. Encryption, history, report serialization, model context and browser formatting preserve these tagged values. Ordinary strings remain strings. Decimal parameters generated by the model use the tool contract `{"type":"decimal","value":"12.50"}`; PostgreSQL/MySQL bind them as numeric values. SQLite rejects native decimal parameters: use reviewed integer minor-unit definitions for exact local money calculations.

Evaluation compares native exact integers/decimals exactly; existing floating-point results retain the evaluator's documented tolerance. Non-finite and oversized exact values are rejected. Previously stored floats cannot recover lost precision; legacy snapshots are labelled `legacy-v1`. This change does not make floating-point source columns or SQLite floating-point arithmetic exact. Connector tests cover normalization and binding paths; live PostgreSQL/MySQL end-to-end verification remains pending.

## Mandatory outbound-model policy

`.env` now includes `MODEL_POLICY_FILE=model_policy.json`. Setup copies `model_policy.example.json` when the local file is missing. The supplied Groq example lists both `openai/gpt-oss-20b` and `openai/gpt-oss-120b`, with **`approved: false`**. Existing endpoint, model and API-key settings are preserved. Model-backed queries are blocked until the operator reviews and explicitly approves a suitable profile in this separate local policy file. Offline/reference checks do not need provider approval.

Every application model invocation, including AI domain drafts, must match exactly one approved endpoint/model profile, an allowed source classification and any local-only requirement. Classifications are `public`, `internal` and `restricted`; unknown sources default to restricted and local-only. Profile approval is an operator assertion, not proof of a provider's contractual or technical guarantees. This is an additional requirement when switching providers: changing `.env` alone does not approve a new destination.

Before binding/invoking the model, a local scanner checks the complete instructions/context for likely credentials, email/phone patterns and payload size. Likely credentials are always blocked. Detected personal information requires both `allow_detected_pii: true` on the approved profile and a separate `pii_sender_groups` grant such as `role:admin` or `group:reviewed_senders`. Neither PII viewing permission nor administrator status alone permits transmission. Rejected API questions and their SQL/context events are scrubbed from saved job snapshots. No rejected payload is logged by this gateway.

Pattern detection is incomplete: names, addresses, obfuscated data or other sensitive facts can escape detection, and ordinary numeric values can trigger false positives. It is not comprehensive anonymization or DLP. For higher assurance, use an approved local deployment and controlled inputs. Model prompts/context can include business metadata, examples and user-supplied text even when result cells are tokenized.

Known LangChain/LangSmith tracing enablement flags are rejected. The SDK client disables automatic redirects and environment-provided proxies, so a response cannot automatically forward the payload to another endpoint. Direct local HTTP is supported only for literal loopback hostnames; remote endpoints require HTTPS. Application policy cannot constrain a malicious provider, independently installed instrumentation, compromised host or custom application code. Provider-side retention, subprocess/system logging and approved network routing still require operational review.
